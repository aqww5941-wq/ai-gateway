# 工程原则与代码通用规范

## 1. 修改前先证明根因

修改前必须形成最小根因说明：

```text
现象：用户或系统看到了什么。
触发条件：什么输入、状态或并发时序会触发。
根因：哪个职责、状态模型或契约不成立。
影响范围：流式/非流式、单机/集群、前端/后端、兼容性与数据。
方案：为什么该修改消除根因，而不是只遮住症状。
验证：哪个测试或复现能在修改前失败、修改后通过。
```

禁止以下止血方式：

- 用额外的 `if err != nil { return nil }` 吞掉错误。
- 用默认值掩盖无效配置，而不在加载阶段拒绝。
- 删除无法正确转换的协议字段，让上游“至少能返回文本”。
- 通过增大超时、重试次数或缓存时间掩盖死锁、慢查询和一致性问题。
- 为通过测试而修改断言，却不解释行为契约为何改变。
- 在多个调用点复制条件分支，而不修复共同抽象或状态机。

## 2. 正确性优先，但不能以放弃体验代替设计

项目同时要求正确性、可靠性和体验。遇到困难时不得把“选择更旧、更弱但看起来稳定的方案”当成默认答案。

### 禁止的偷懒式降级

- 配额存储失败时绕过配额继续计费请求。
- 目标不支持 Tools 时删除 `tools` 后继续请求。
- 集群 Redis 故障时静默切到各实例内存状态。
- 管理接口失败时隐藏前端功能入口。
- 热重载不完整时只更新部分组件并声称配置已生效。
- 新方法出现可修复问题时，直接永久切回体验或能力明显更差的旧方法。

### 允许的韧性机制

只有同时满足以下条件才允许重试、Fallback 或功能降级：

1. 行为有设计或明确配置，不是临时分支。
2. 不破坏安全、租户、账务、数据一致性和请求语义。
3. 替代目标满足请求能力，用户不会得到伪造的等价结果。
4. 降级状态、原因、范围和恢复结果可通过日志、指标或健康接口观察。
5. 有测试覆盖正常、进入降级、恢复和降级失败路径。

若无法满足，应明确失败并提供可操作错误，而不是伪造成功。

## 3. 职责与依赖

- 保持单一职责，协议转换、传输、路由、持久化和 HTTP 展示层不要混在同一抽象中。
- 优先修复拥有错误状态的组件，不在上层重复猜测和修正。
- 避免跨包共享可变状态；并发读取的运行时配置使用不可变快照或明确同步。
- 新依赖必须说明用途、替代方案、维护状态、二进制/运行成本和安全影响。
- 公共接口、数据库 Schema、安全边界或兼容性变化必须先更新 ADR/设计，再编码。

## 4. 错误处理

- 错误必须保留原因链，Go 中使用 `%w` 包装需要上层分类的错误。
- 区分输入错误、能力不兼容、限流、上游 429、5xx、超时、取消、协议错误和内部依赖错误。
- 不用字符串匹配代替稳定的错误类型或 `errors.Is/As`。
- HTTP 错误应稳定、可机器识别，并携带安全的请求追踪标识；不要把内部堆栈或上游秘密返回给客户端。
- `context.Canceled` 和 `context.DeadlineExceeded` 不得被普通重试逻辑吞掉。

## 5. 变更范围

- 一个提交解决一个可描述的问题，不同时跨越无关的协议、存储、控制面和前端重构。
- 发现相邻问题可以记录在 changelog 风险或后续项中，不擅自扩大本次范围。
- 纯机械重命名与行为修改尽量分开，保证 diff 可审查。
- 不手工修改 `web/dist/` 或 `internal/static/dist/` 中的生成文件。
