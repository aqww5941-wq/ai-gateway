# 建立 v3 逐任务实施基线

- 日期：2026-08-06 09:03 CST
- 类型：L1
- 关联需求：N/A
- 影响模块：`docs/AI_Gateway_v3_项目实施任务书.md`、`AGENTS.md`、`.rules/**`、v3 设计文档

## 根因

v3 设计只定义了 M0～M6 七个大里程碑，每个阶段同时包含架构、代码、测试、配置、迁移和文档，跨度达到数天至数周。直接按里程碑实施会形成难以审查和回滚的大提交，也没有唯一当前任务、前置依赖和逐项完成证据。

## 解决方案

新增 v3 项目实施任务书，将完整项目拆为 Task 1～Task 62，并设置 M0～M6 七个 Exit Gate。每个 Task 明确状态、依赖、目标、交付物、验收、验证和不包含范围；同一时间只允许一个 Task 实施，完成验收、changelog 和原子提交后才释放下一项。

根据当前仓库实测补充基线证据，并将任务书接入根 AGENTS、项目规则、交付工作流和 v3 设计。计划外必要工作通过 Remediation Task 显式插入，禁止顺带扩大当前范围。

## 行为与兼容性

本次只改变项目治理和实施文档，不修改运行时 API、配置、数据库或构建行为。Task 1 为唯一 Ready 项，Task 2～Task 62 为 Pending；Task 36 是秋招三厂商闭环，Task 62 是最终项目完成条件。

## 可观测性

不适用，无运行时代码变化。未来运行时 Task 已分别包含日志、指标、Trace 和诊断证据要求。

## 验证

- `[通过]` Task 标题严格连续为 1～62，无重复或缺号。
- `[通过]` 状态统计为 1 个 Ready、61 个 Pending。
- `[通过]` M0～M6 Exit Gate 分别对应 Task 10、18、27、36、44、55、62。
- `[通过]` `go test ./...`、`go vet ./...`、`go build ./cmd/gateway`，用于校准当前基线。
- `[通过]` `git diff --check`。
- `[未执行]` 前端 build；本次不改变前端或构建配置，现有产物双事实源留给 Task 2 处理。

## 风险与回滚

任务颗粒度可能随实现发现的新根因调整，但必须先修改任务书并插入显式 Remediation Task，不能降低 Exit Gate。回滚可恢复本提交中的文档和治理入口，不涉及数据迁移。用户此前删除的 v2 文档不纳入本任务提交。
